# Conversation front end and application focus

The conversation front end is the participant's user-facing entry point. It
owns turn order, interruption, short conversation history, top-level delegation,
and delivery through the shared voice aggregation path. It does not own an
application's tools, prompts, workflow, or background work. The generic
conversation capability answers ordinary chat and current-view questions with
the same direct visual behavior as the simple VLM sample.

## Routing and focus

The first tier selects among a small number of clearly distinct capabilities:
generic conversation and the registered application agents. Each application
owns its high-level routing description and a bounded, read-only context
projection. Its leaf-tool instructions and examples remain inside the
application. Adding a leaf tool must not require an edit to the front-end
prompt. A registration may contribute brief routing examples, but those
examples remain owned beside the application.

When no application holds focus, the front end may answer locally, inspect the
current view, or delegate one turn to an application. A stateless application
returns control after that turn; the next utterance is routed again. An
application may instead claim focus for a participant. While it holds focus,
ordinary utterances go directly to it without another top-level model call.
The application interprets requests to leave its mode and releases focus; the
front end must not infer an exit from a generic word such as "stop." Explicit
client controls may provide a recovery exit if an application cannot respond.
Participant departure releases focus and resources. Interrupting a response
cancels that turn, not the application focus.

XR render demonstrates stateless delegation: every new utterance reaches the
front end, and XR scene work goes to the existing scene supervisor. Tea making
demonstrates application focus: the tea application includes its foreground
guide and background capabilities, claims focus for its active workflow, and
releases it on a user-requested exit. The simple VLM example always selects
the generic conversation capability. None of these arrangements changes the
sample-owned inner prompts or tool ownership.

## Conversation and voice

The front end keeps the spoken conversation across generic and application
turns. The generic capability receives recent turns and a small application
context projection so follow-up questions remain meaningful without exposing
an application's private tool catalog. Context describes facts the application
is willing to share; it is not an instruction to the generic capability and
cannot authorize an application action. Current visual questions still require
fresh camera evidence.

The generic path gives the answer directly and does not emit a preliminary
acknowledgement. After application delegation, the selected application may
emit one contextual acknowledgement and useful progress through the voice
aggregation path. The front end must not speak a competing acknowledgement
before it knows which capability owns the turn. All outputs retain the
originating participant and turn identity, and superseded output is cancelled.

## Evaluation contract

Evaluate complete turns, not only the first tool call. Each case records the
input and relevant app state, selected capability, focus transition, tools or
effects, acknowledgement and progress, and final speech. Cover ordinary chat,
current visual follow-ups, application actions and questions, mixed requests,
past observations, quoted or negated commands, active-mode exits, interruptions,
and multiple participants. Measure time to first audible response as well as
routing accuracy and total completion time. Compare the same corpus with Nano
Omni and Lightning, including bounded thinking where it improves the
accuracy-latency tradeoff. Keep held-out cases separate from prompt tuning.

The isolated first-tier corpus lives in `agent-samples/common/shared-agents/eval/`.
From the repository root, with the shared language endpoint already serving,
run:

```bash
uv run --project agent-samples/common/shared-agents --with pyyaml \
  python agent-samples/common/shared-agents/eval/routes.py
uv run --project agent-samples/common/shared-agents --with pyyaml \
  python agent-samples/common/shared-agents/eval/routes.py \
  --corpus agent-samples/common/shared-agents/eval/routes_challenge.yaml
uv run --project agent-samples/common/shared-agents --with pyyaml \
  python agent-samples/common/shared-agents/eval/routes.py \
  --corpus agent-samples/common/shared-agents/eval/routes_synthetic.yaml
```

The synthetic corpus registers several imaginary applications at once. It
checks overlapping domains, contextual follow-ups, and whether underspecified
requests get a clarification question rather than an arbitrary delegation.
These checks measure idle-turn decisions and model-call latency. Focus capture,
release, participant isolation, and spoken-result history are covered by
`tests/test_sample_front_end.py`; neither layer replaces live audio and
application-effect checks.
