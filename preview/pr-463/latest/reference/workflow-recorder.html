Workflow recorder#

The workflow recorder is a standalone sample at agent-samples/workflow-recorder/. Its orchestrator starts DeviceIOHub and a worker that composes RecorderAgent, SopEngineAgent, and VoiceAgent in one runtime. It reuses Parakeet STT, Nemotron Omni, Cosmos VLM, and Piper TTS from the shared model-server stack. Refer to the sample README for launch commands.

Configuration#

Run and edit the sample from agent-samples/workflow-recorder/. The orchestrator passes yaml/device_io_hub.yaml to the hub and yaml/workflow_recorder_worker.yaml to the worker. Paths in the worker YAML resolve relative to that YAML file, including the model profile, voice-gate configuration, artifacts directory, and guides directory.

File

Owns

yaml/workflow_recorder_worker.yaml

Capture and caption intervals, SOP generation timeout, guide scanning, output paths, frame limits, VAD, and idle timeout

yaml/models.json

Model adapters, endpoints, readiness, and reuse declarations

yaml/voice_gate.yaml

Wake phrases, listening chime, and follow-up window

yaml/device_io_hub.yaml

Room and ports, web and token servers, and network behavior

Restart workflow_recorder after editing configuration. Editing the model profile changes the worker’s endpoints; it does not reconfigure the persistent model servers. Refer to Customizing model servers for changes to model deployment, and to Sample configuration reference for checked-in values and field comments.

Record a demonstration#

The agent welcomes each participant once on connection and explains the recording commands. Connecting leaves the recorder idle. Enable camera and microphone in the client, then use these commands as separate utterances:

  1. Say start workflow. The agent says: “Workflow recording started. Demonstrate and narrate the steps, then say finish workflow.”

  2. Demonstrate the procedure and narrate its steps. Narration is recorded without SOP-engine replies or command reminders.

  3. Say finish workflow. Recording stops and conversion to a draft SOP starts automatically. The agent announces that it is creating a draft SOP, then announces the short guide name when the draft is ready.

The commands are case-insensitive and also accept an optional hey agent prefix. Keep magic_phrases: [] in yaml/voice_gate.yaml so that both the commands and ordinary narration reach the recorder. Typed client messages use the same command and narration handling. Control utterances are not included in the recorded instructions.

Recording samples frames, saves accepted final speech transcripts, and produces periodic frame-linked visual captions with an Activity → Phase summary. Captions use the prior observation and up to eight recent narration records from the preceding 30 seconds, never speech timestamped after the selected frame. Narration directs visual attention but does not prove that an action happened. Starting a recording stops any active SOP execution for that participant. Repeating start workflow does not create another recording; repeating finish workflow during conversion does not create another guide.

Session packets are written under artifacts/sessions/. Each packet includes packet.json, a frame index, transcript.jsonl, captions.jsonl, and summary.md. The default capture rate is two frames per second and the caption interval is five seconds. This prototype has no retention policy; remove old session folders when their frame data is no longer needed.

Disconnecting or stopping the worker during recording preserves an interrupted packet without generating a guide. Reconnecting leaves the recorder idle; say start workflow for a new recording. An explicit finish workflow is required for automatic conversion.

Generate and approve a guide#

After finish workflow, the configured LLM converts timestamped narration and visual captions into ordered SOP steps. The automatic converter uses captions rather than reanalyzing the saved images. Each step cites recorded evidence and notes uncertainties. The worker validates the generated guide and writes a draft workflow_<id>.guide.yaml into guides/, without overwriting an existing guide. Review the steps, visual completion conditions, evidence, and uncertainties against the recording, then set task.status to approved before use.

The generator starts from narration: every recorded utterance must be assigned to a step as action evidence or interpreted context. Distinct actions become steps; sentence fragments, destinations, clarifications, and corrections refine the relevant step instead of becoming extra steps. Incidental or unclear speech remains explicitly non-operative context, separate from actionable clarifications. The model first classifies whether a procedure exists; a negative decision ends conversion without retrying it into an invented procedure.

For each step, the model selects at most one caption that best matches the combined instruction and context, considering objects, locations, counts, state, and time rather than timestamp alone. The generated step’s voice.prompt retains the original caption, its frame ID, utterance context, and a narration-refined caption. Raw captions.jsonl records are not changed. The refinement distinguishes observed state from narrated intent and marks conflicts or missing visual confirmation as uncertainty. If no caption is relevant, the step remains grounded in speech with an explicit visual-evidence gap.

Completion conditions describe the full narrated requirement, including counts, locations, and later corrections, not merely the partial state in a caption. They are used in both the generated state description and the image-check question. A partial result must not satisfy a complete-step check.

The converter uses a separate schema-constrained client to the configured LLM endpoint; the endpoint must support JSON-schema response formatting. This does not constrain ordinary agent chat. The converter also decodes plain JSON, fenced JSON, and bounded text-block envelopes, including stringified envelopes, without executing model output. It validates the resulting draft and requires every speech ID to be accounted for. Invalid output or missing coverage gets one corrective retry within the same generation timeout. A second invalid response fails conversion without saving a partial guide. These checks enforce structure and evidence references, not semantic correctness; review the interpreted context, selected captions, and completion conditions before approving a guide.

SOP generation enables model reasoning for grouping utterances and matching captions. For the sample’s Nemotron model, it supplies a reasoning_budget hint of 2,048 tokens unless the model profile already specifies one. The hard response limit is 8,000 tokens, and the configured total generation timeout still applies.

The session’s generation.json reports generating, draft (with the guide ID and path), failed (with an error), or interrupted if the worker stops during conversion. Conversion continues if the participant disconnects after finish workflow, but the completion announcement is not sent to a new connection. Wait for conversion to finish before starting another recording for that participant.

Automatic conversion supports up to 24 steps and approximately 60,000 characters of transcript/caption evidence. Model calls have a configurable guide_generation_timeout_s (default 120 seconds). Empty evidence, oversized recordings, invalid model output, and model failures preserve the recording without publishing an invalid guide. As a manual alternative, point a skill-aware coding agent at skills/recording-to-guide/ and the session packet to create or refine a draft using the saved images as well.

The running sample discovers and validates guides automatically and writes artifacts/guide-index.json. Invalid and draft guides are visible in the index but cannot run. A fresh checkout contains no executable guides.

Validate a guide from agent-samples/workflow-recorder/:

uv run --project worker python -m workflow_recorder_worker._validate_guide guides/my-workflow.guide.yaml

Name and rename a guide#

The generator suggests a short spoken name of one to four words in task.name. This is the editable name used by list guides and start guide <name>. There is no numbering scheme. The internal task.id and filename remain stable when the name changes.

For example, edit the existing name field in a guide YAML:

task:
  id: workflow_c00616189681
  name: Hand Gestures
  # Keep the remaining task fields unchanged.

Save the file, allow the catalog scan to pick it up (two seconds by default), then say or type start guide hand gestures. The guide must still be approved. Name matching ignores case and repeated whitespace. Existing guides with longer names remain valid; shorten their task.name manually if desired.

Use distinct names within the guide library. If multiple guides share a name, the engine asks you to edit their names or select one by its internal ID; it never chooses one arbitrarily. Existing ID and unambiguous ID-prefix selection remain supported. A running guide keeps its pinned name and content until stopped; edits apply to subsequent runs without a worker restart.

Run an SOP#

The engine accepts explicit commands through the connected client:

Command

Action

start workflow

Start recording a demonstration; stop any active SOP execution

finish workflow

Stop recording and generate a draft SOP

list guides

List valid guides and their approval status

start guide <name>

Start an approved guide by its editable task.name; IDs also work

guide status

Report the current step

next or continue

Advance after the current step is complete

skip

Skip an incomplete step

restart guide

Restart the active guide

stop guide

Stop the active guide

Questions during a run are answered in the context of the current step. The SOP commands other than finish workflow are treated as narration while recording; finish the recording before listing or running guides. The engine maintains typed participant-local state, periodically observes steps, and checks evidence and state revisions before committing updates. Steps never advance automatically. Each run pins the guide’s exact version and SHA-256 content generation; catalog edits affect future runs only.

Verify changes#

Run the recording-state and conversion regression tests from the repository root:

uv --config-file uv.toml run --project tests pytest tests/test_workflow_recorder.py

With the shared model servers running, run the live-model evaluation from agent-samples/workflow-recorder/:

uv run --project worker python eval/eval.py

The evaluation uses synthetic recordings in temporary directories; it does not read or modify saved user recordings. Cases check chronological actions, rejection of incidental conversation, embedded instruction handling, and acknowledgment of conflicting evidence. They also check distinct attachments under repeated captions, multiple actions in one utterance, and a final narrated action without a caption. Additional cases check fragmented speech, caption relevance, requested counts despite partial observations, and later corrections. These checks complement human review of generated SOPs; they do not establish correctness for every procedure.
